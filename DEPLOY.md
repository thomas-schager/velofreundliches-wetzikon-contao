# Deployment Guide — VeloWetzikon Contao

This document describes every step needed to move the local Contao installation
to the production web host. Keep it up to date whenever the local setup changes.

> **Assumed hosting scenario:** Shared web hosting without SSH/console access.
> Commands shown for SSH exist as a reference; the shared-hosting alternative
> is always listed. If SSH becomes available later, the SSH path is faster.

---

## Prerequisites

### Local machine
- PHP >= 8.1 (currently 8.5)
- Composer >= 2
- Git
- FTP client (e.g. Cyberduck, FileZilla) or rsync over SFTP

### Web host requirements
- PHP >= 8.1 with extensions: `intl`, `dom`, `mbstring`, `gd` (or `imagick`), `pdo_mysql`, `zip`, `openssl`, `curl`
- **MariaDB** (recommended, tested locally with MariaDB 12.3) — MySQL 9.x is NOT compatible due to reserved keyword conflicts; use MariaDB or MySQL 8.4 LTS on the host
- A dedicated web root that can be pointed to the `public/` sub-folder
- phpMyAdmin or equivalent for database management
- cPanel or similar panel to configure PHP settings and cron jobs

## 1. Local Development Setup

### First-time installation
```bash
# Already done — Contao 5.7 installed via:
composer create-project contao/managed-edition .
```

### Environment file
Copy `.env` to `.env.local` and fill in your local database credentials:
```
DATABASE_URL=mysql://user:password@127.0.0.1:3306/velowetzikon?serverVersion=mariadb-12.3.2
APP_SECRET=<random 32+ char string>
```

`.env.local` is git-ignored and never committed.

### Run locally
```bash
# PHP built-in server (quick test only)
php -S localhost:8000 -t public/
```

### Database migrations and admin user (local)

Contao 5 has no web-based install tool. Use the CLI:

```bash
# Apply pending database migrations
php bin/console contao:migrate --no-interaction

# Create the first backend admin user
php bin/console contao:user:create
```

## 2. Git Workflow

### What is committed
| Path | Committed | Reason |
|---|---|---|
| `composer.json` | Yes | Dependency definitions |
| `composer.lock` | Yes | Reproducible installs |
| `system/config/` | Yes | App config (not `localconfig.php`) |
| `templates/` | Yes | Custom Twig templates |
| `contao/` | Yes | DCA extensions |
| `src/` | Yes | Custom PHP controllers |
| `files/themes/` | Yes | Theme CSS, fonts, static images |
| `.env` | Yes | Default env vars (no secrets) |
| `vendor/` | **No** | Re-installed via Composer locally, then uploaded |
| `public/` | **No** | Generated by Contao |
| `assets/` | **No** | Generated component assets |
| `files/div/` | **No** | User-uploaded media (managed separately) |
| `var/` | **No** | Cache & logs |
| `.env.local` | **No** | Contains secrets |

> **Note on `files/themes/`:** Theme CSS, fonts, and static images are part of the
> codebase and live under `files/themes/velo/`. They are committed to Git and
> uploaded as part of the code deploy — not treated as user content.

### Push to GitHub
```bash
git remote add origin git@github.com:YOUR_USER/YOUR_REPO.git
git push -u origin main
```

## 3. Deploying to the Web Host (Shared Hosting / No SSH)

Since console access is unavailable, every step that would normally be a CLI
command has an alternative listed below.

### 3.1 Prepare locally before uploading

Run these once on your local machine before each upload:

```bash
# Build the production vendor/ directory (no dev dependencies)
composer install --no-dev --optimize-autoloader

# Verify there are no obvious errors
php bin/console cache:warmup --env=prod
```

This generates an optimised `vendor/` folder that you upload to the server.
You do **not** need Composer on the server.

### 3.2 What to upload

Upload the following via FTP/SFTP to the server (the project root, not inside `public/`):

| What | Notes |
|---|---|
| `vendor/` | Built locally in §3.1 — large, ~150 MB |
| `composer.json` + `composer.lock` | For reference |
| `bin/` | Symfony console (not used directly on shared hosting, but needed for Contao internals) |
| `config/` | Symfony config |
| `contao/` | DCA extensions |
| `src/` | Custom controllers |
| `templates/` | Twig templates |
| `files/themes/` | Theme CSS, fonts, images |
| `files/div/` | User-uploaded media (sync separately, see §4) |
| `public/` | The web root — upload everything **except** `public/files/` (generated by Contao) |
| `.env` | Base env file |

**Do not upload:** `var/`, `assets/` (generated on first request).

**Upload separately (once, not on every deploy):**
- `public/files/themes/velo/css/` — copy the CSS files here as real files (see §8.1)
- `public/files/themes/velo/fonts/` — copy the font files here as real files (see §8.1)

### 3.3 Configure the environment on the server

Create `.env.local` directly on the server (via FTP or the host's file manager):

```
APP_ENV=prod
APP_DEBUG=0
APP_SECRET=<generate with: openssl rand -hex 32>
DATABASE_URL=mysql://dbuser:dbpassword@localhost:3306/dbname?serverVersion=mariadb-X.X.X
MAILER_DSN=smtp://user:pass@smtp.host:587
```

`APP_SECRET` must be a new random string, different from local. Generate one with
`openssl rand -hex 32` on your local machine.

### 3.4 Configure the web root

Point the host's document root to the **`public/`** subfolder, not the project root.
In cPanel this is usually done via "Domains" → subdomain or domain → "Document Root".

### 3.5 Run database migrations and create admin

Contao 5 has no web-based install tool. On a host without SSH, use the
**Contao Manager** — a single PHAR file that provides a browser-based maintenance UI.

**One-time setup of the Contao Manager:**
1. Download `contao-manager.phar` from `https://download.contao.org/contao-manager/stable/contao-manager.phar`
2. Rename it to `contao-manager.phar.php`
3. Upload it to the `public/` directory on the server
4. Visit `https://yourdomain.com/contao-manager.phar.php` in a browser
5. Follow the setup wizard — it will prompt for database credentials and run migrations

The Contao Manager can also clear caches, run `contao:migrate`, and manage packages.
Keep the file on the server for future maintenance; protect it with a strong password.

**If SSH is available**, skip the Manager and use the CLI instead:
```bash
php bin/console contao:migrate --no-interaction
php bin/console contao:user:create
```

### 3.6 Register uploaded files in Contao

After uploading `files/`, Contao's internal file database (DBAFS) must be
synchronised. Do this from the **Contao backend**:

**System → Maintenance → Synchronize files** (German: *Dateien synchronisieren*)

This is the browser equivalent of `php bin/console contao:filesync`.

### 3.7 Verify theme CSS is accessible

Because Contao's symlink mechanism cannot run without SSH (see §8.1), the CSS and
font files must be present as **real files** (not symlinks) at:

```
public/files/themes/velo/css/   ← copy of files/themes/velo/css/
public/files/themes/velo/fonts/ ← copy of files/themes/velo/fonts/
```

Upload these once via FTP. On subsequent code deploys, re-upload them whenever the
CSS changes. Verify with:

```
https://yourdomain.com/files/themes/velo/css/site.css  → should return 200
```

### 3.8 Warm up images

Visit each main page in a browser:
- `/` (Start)
- `/die-mission`
- `/themen`
- `/veranstaltungen`
- `/stellungnahmen`
- `/ueber-uns`

This re-generates the deferred image resize configs in `var/deferred-images/`.
Images on these pages will load correctly after the first visit (see §8.3).

## 4. File Uploads / User Content

The `files/div/` folder contains user-uploaded media and is **not** in Git.

**Initial upload (local → server):**

Use an FTP client to upload the entire `files/div/` folder.

If rsync over SSH is available:
```bash
rsync -avz files/div/ user@host:/path/to/site/files/div/
```

**After uploading**, synchronise the Contao file database via the backend:
System → Maintenance → Synchronize files.

## 5. Database

The database is **not** in Git.

### First deployment (export local → import on host)

**Export locally:**
```bash
mysqldump -u root velowetzikon > velowetzikon_$(date +%Y%m%d).sql
```

**Import on the host:**
- Open phpMyAdmin on the host
- Select the target database
- Use "Import" → choose the `.sql` file

> Some shared hosts limit phpMyAdmin upload size to 2–8 MB. If the dump is larger,
> split it with `--extended-insert=false` or use the host's own import tool, or
> ask support to import via the command line.

### After code updates (migrations only)

Run migrations via the Contao Manager (`/contao-manager.phar.php` → Maintenance →
Database migrations), or via SSH:
```bash
php bin/console contao:migrate --no-interaction
```

## 6. PHP Configuration (Upload Limits)

Shared hosts often default to low upload limits (2–8 MB). Contao backend uploads
(images, documents) need at least 20 MB.

**Set via `.user.ini`** — create/upload this file to the `public/` directory:
```ini
upload_max_filesize = 20M
post_max_size       = 25M
memory_limit        = 256M
```

Alternatively configure via cPanel → PHP Settings (if available).

Verify the setting is active by checking System → Info in the Contao backend.

---

## 7. Cron Jobs

Contao requires a periodic task runner for scheduled items (newsletter dispatch,
purge expired sessions, etc.).

**Via cPanel Cron Jobs** (if available):
```
* * * * * /usr/bin/php /path/to/site/bin/console contao:cron
```

**Via URL-based cron** (fallback for hosts without shell cron):

Contao also accepts a web-triggered cron at:
```
https://yourdomain.com/_contao/cron
```
Use the host's "URL cron" feature or an external service (e.g. cron-job.org) to
ping this URL every minute.

## 8. Known Issues and Gotchas

### 8.1 Theme CSS/font files — symlinks vs. real files

**Background:** On the local dev machine, `public/files/themes/velo/css` and
`public/files/themes/velo/fonts` are symlinks created manually (because Contao's
`contao:symlinks` command doesn't auto-create them — the folders are not flagged
as publicly accessible in the DBAFS).

**On a shared host without SSH,** symlinks cannot be created via FTP. The solution
is to upload the CSS and font files as **real copies** to:

```
public/files/themes/velo/css/      ← copy from files/themes/velo/css/
public/files/themes/velo/fonts/    ← copy from files/themes/velo/fonts/
```

These are the same files that live in `files/themes/velo/`. They must be kept in
sync manually: whenever you update a CSS file, re-upload it to both locations.

**On a host with SSH**, create symlinks instead (better, avoids duplication):
```bash
ln -s ../../../../files/themes/velo/css   public/files/themes/velo/css
ln -s ../../../../files/themes/velo/fonts public/files/themes/velo/fonts
```

**Permanent fix (works for both):** In the Contao backend, go to
Dateiverwaltung → `files/themes/velo/css` → attributes → mark as
"publicly accessible". Repeat for `fonts/`. After that, `contao:symlinks` handles
it and the manual step is no longer needed. This requires running `contao:symlinks`
on the host (SSH) or the backend maintenance step above.

---

### 8.2 PHP upload limits

**Symptom:** Uploading images larger than ~2 MB fails in the Contao backend.

**Local (Homebrew PHP):** Created `/opt/homebrew/etc/php/8.5/conf.d/velo-upload.ini`:
```ini
upload_max_filesize = 20M
post_max_size       = 25M
memory_limit        = 256M
```
Restart the PHP built-in server after creating this file.

**On the host:** Use `.user.ini` in `public/` (see §6) or cPanel PHP settings.

---

### 8.3 Images return 404 after cache clear

**Symptom:** Processed images (URLs like `/assets/images/1/filename-hash.jpg`)
return 404 after clearing the cache.

**Cause:** Contao uses deferred image resizing. When a page renders, it writes a
resize config to `var/deferred-images/deferred/`. The image is only actually resized
when first requested. Clearing `var/` deletes these configs, so subsequent image
requests fail until the pages are re-rendered.

**Fix:** Visit each page in a browser once after any cache clear. The configs are
re-written and images resolve on the next request.

No data is lost — original files in `files/` are always intact.

---

### 8.4 Clearing the cache without SSH

Contao caches compiled templates and container config in `var/cache/prod/`.

**Via Contao backend:**
System → Maintenance → Rebuild cache (German: *Produktiv-Cache neu aufbauen*)

**Via FTP (manual):** Delete the contents of `var/cache/prod/` using the host's
file manager. Leave the `var/` directory itself in place.

> Do **not** delete `var/deferred-images/` unnecessarily — doing so triggers the
> image 404 issue described in §8.3. Only delete `var/cache/`.

## 9. Checklist Before Going Live

**Code & files**
- [ ] `composer install --no-dev --optimize-autoloader` run locally
- [ ] All code + `vendor/` uploaded to server
- [ ] `files/div/` (user media) uploaded to server
- [ ] `public/files/themes/velo/css/` uploaded as real files (see §8.1)
- [ ] `public/files/themes/velo/fonts/` uploaded as real files (see §8.1)

**Environment**
- [ ] `.env.local` created on server with `APP_ENV=prod`, `APP_DEBUG=0`, strong `APP_SECRET`, correct `DATABASE_URL`
- [ ] Web root points to `public/` subfolder only
- [ ] PHP upload limit ≥ 20M configured (see §6 / §8.2)
- [ ] SSL certificate active (`https://`)

**Contao setup**
- [ ] Database migrated and admin account created via Contao Manager (`/contao-manager.phar.php`) or CLI (`contao:migrate` + `contao:user:create`)
- [ ] Contao backend → System → Maintenance → Synchronize files (DBAFS sync)
- [ ] Contao backend → System → Maintenance → Rebuild cache
- [ ] Warm-up: visit each main page once so images render correctly (see §8.3)
- [ ] Cron job configured (see §7)

**Verification**
- [ ] `https://yourdomain.com/files/themes/velo/css/site.css` → 200 OK
- [ ] Homepage loads with correct styling and images
- [ ] Contao backend login works (`/contao`)
- [ ] Test image upload in backend (check ≥ 8 MB file succeeds)
- [ ] Contao Manager password set (the wizard prompts for this on first use)
